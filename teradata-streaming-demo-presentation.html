TERADATA STREAMING DEMO  ·  FIELD GUIDE

From Kafka to Vantage, six different ways.

A hands-on tour of Teradata's real-time and near-real-time ingestion paths — Avro BLOBs, TPT STREAM, Kafka Connect, Apache Flink, Native Object Store, and Open Table Format — running on a docker-compose stack you bring up on a laptop and point at a real Teradata instance. Every demo here is bash demos/<name>/run.sh away from a row landing in Vantage.

Where Teradata fits

Teradata isn't another streaming engine — it's the analytical layer underneath one.

Teradata does not compete with Apache Kafka, Apache Flink, or any message broker. It is the enterprise SQL, governance, and historical-context layer that sits over streaming data — and it connects to a live Kafka topic through two integration paths that typically run in parallel.

Hot path — events land in Teradata directly. TPT's Kafka Access Module and STREAM operator write straight into Teradata block storage (BFS). Latency is bounded by the flush interval — this is Demo 02's path, and the one to reach for when a dashboard or operational query needs sub-5-second freshness.
Cold path — events land in object storage first. Flink or Kafka Connect write to Iceberg or raw files on object storage; Teradata queries that data live through OTF or NOS, with no copy step. This is the path Demos 03–05 build, and the default for shared, governed data products.

Three ways in
TPT

The streaming workhorse

The highest-throughput path into Teradata. Five tuning levers govern it in production:

  • MaxSessions = AMP count — the primary throughput lever; each session maps to a parallel AMP thread.
  • Format: CSV is fastest; JSON needs pre-shredding; Avro/Protobuf must be decoded upstream (Flink pre-processor).
  • BufferCapacity: raise from the 64KB default to 1–4MB for high-throughput ingest.
  • ErrorLimit > 0 in production — at 0, one bad message halts the entire job.
  • TASM: a dedicated HIGH-priority workload tier keeps ingest sessions from being preempted.
Kafka Connect

The managed alternative

The Teradata Sink Connector — declarative, schema-aware, no TPT job scripts:

  • Schema-aware via Schema Registry (Avro/Protobuf) — no custom deserialisation code.
  • Auto-creates tables from the Kafka topic schema.
  • Offset management and fault tolerance built in.
  • Not built for extreme throughput (1B+ msg/hr) — that's TPT's job.
  • Auto-evolution is limited: type changes and column removal aren't supported.
Apache Flink

Three integration roles

Flink 2.0 is the de facto stream processing engine. It meets Teradata three distinct ways:

  • JDBC Lookup Enrichment — real-time lookup joins against Teradata reference data (Demo 05).
  • Iceberg Writer → OTF — Flink transforms and writes Iceberg; Teradata queries it live (Demo 04).
  • Avro/Protobuf pre-processor — decodes binary formats TPT can't read natively, republishing as JSON/CSV for TPT to ingest.
Production design patterns

Three patterns account for most enterprise streaming deployments built on Teradata. The mixed pattern — hot and cold paths running in parallel off the same topic — is the most common in production.

PatternFlowBest forReference benchmark
1 · Event Processing & Enrichment Kafka → Flink → Teradata JDBC lookup → enriched stream → consumers Fraud detection, next-best-offer, anomaly detection Global bank: 37 hrs → 12 min fraud detection
2 · Real-Time Dashboard Kafka → TPT Stream → Teradata tables → BI tools (live) Logistics tracking, NOC monitoring, financial dashboards 2.5M+ queries/day concurrent with live ingest
3 · Mixed / Mini-Batch (most common) Kafka → TPT (staging) → mini-batch ETL and Kafka → Flink → Iceberg → OTF, in parallel Decoupled hot + cold paths; the majority of enterprise streaming estates DHL: 500M msg/day; European retailer EPOS streaming

This guide's six demos are smaller-scale instances of the same three patterns: Demo 05 is Pattern 1, Demo 02 is Pattern 2, and Demos 03–04 together are Pattern 3's cold path.

Demo 01 · File ingestion

01Avro BLOB → DATASET column

Loading Avro container files into a Teradata DATASET STORAGE FORMAT AVRO column via a single restartable TPT STREAM job, with schema evolution across two file versions.

Ingestion: TPT STREAM + DataConnector Feature: schema evolution · restartable multi-file load
What it demonstrates
  • TPT STREAM is the only high-throughput TPT operator that supports BLOB/CLOB columns — LOAD (FastLoad) and MLoad both reject LOB columns at job start; STREAM accepts them.
  • BLOB(size) AS DEFERRED BY NAME is the TPT schema attribute for a BLOB column whose value is a file path — DataConnector reads the bytes at that path and passes them to STREAM.
  • Manifest-based multi-file loading — a single TPT job processes a pipe-delimited manifest of N files; both container files are loaded in one restartable job.
  • Schema evolution without ETL rewrites: v1 records (5 fields) and v2 records (8 fields) coexist in the same DATASET AVRO column; querying a v2 field on a v1 row returns NULL.
  • Dot-notation access (avro.."field_name") and AVRO_CHECK() for inline validation.
How to run
terminal
# From project root
bash demos/01-avro-blob/run.sh
Why a dedicated split operator? The Avro Object Container File format wraps each record in file-level framing — sync markers and an embedded schema header. AvroContainerSplit is the table operator built to walk that structure and emit one row per Avro record; a plain CAST operates on a single value and has no concept of that framing.
How it works
1

Generate Avro container files + manifest

fastavro writes binary Avro Object Container File format. The schema carries no namespace, since a namespace produces a dotted record name, and Teradata's Avro 1.7.7 parser reads only unqualified record names. A pipe-delimited manifest lists each file path.

kafka/producers/generate_product_avro.py
2

TPT STREAM load — BLOB(size) AS DEFERRED BY NAME

DataConnector reads the manifest, opens each file path, and streams the raw bytes to the STREAM operator. Both container files are loaded in a single restartable job; twbrmcp ttuuser clears any previous checkpoint before each run.

tpt/tbuild/avro_blob_load.tbuild → avro_product_stage
3

Split with AvroContainerSplit

A FROM-clause table operator: ON (key_col, blob_col) → returns (out_container_id, avro_object_id, avro_value), one output row per Avro record in the container.

4

Query with dot notation

avro.."field_name" for recursive field access; AVRO_CHECK(avro) to validate individual rows.

Tables & code
-- Staging: one row per .avro file (BLOB)
CREATE TABLE avro_product_stage (
  stage_id  INTEGER NOT NULL,
  container BLOB
) PRIMARY INDEX (stage_id);

-- Target: one row per Avro record (DATASET AVRO)
CREATE MULTISET TABLE avro_product (
  container_id  INTEGER,
  avro_obj_id   INTEGER,
  avro          DATASET(2097088000) INLINE LENGTH 64000 STORAGE FORMAT AVRO
) PRIMARY INDEX (container_id);
-- avro_manifest.txt format (pipe-delimited):
--   1|/tpt/data/sample/product_v1.avro
--   2|/tpt/data/sample/product_v2.avro

-- TPT STREAM operator schema (avro_blob_load.tbuild):
--   stage_id  VARCHAR(10)
--   container BLOB(10000000) AS DEFERRED BY NAME   ← key syntax

-- decode.bteq: split the container, then verify
INSERT INTO demo_db.avro_product
SELECT T.out_container_id, T.avro_object_id, T.avro_value
FROM AvroContainerSplit (
  ON (SELECT stage_id, container FROM demo_db.avro_product_stage)
) AS T;

SELECT AVRO_CHECK(avro) AS validity, COUNT(*) AS cnt
FROM demo_db.avro_product GROUP BY 1;
-- All records with dot-notation field access
SELECT
  container_id                AS schema_version,
  avro.."product_id"          AS product_id,
  avro.."name"                AS name,
  avro.."price"                AS price,
  avro.."description"         AS description,   -- NULL for v1 rows
  avro.."discount_pct"        AS discount_pct   -- NULL for v1 rows
FROM demo_db.avro_product
ORDER BY 1, 2;

-- Records above a price threshold
SELECT avro.."product_id", avro.."price", avro.."discount_pct"
FROM demo_db.avro_product
WHERE avro.."discount_pct" > 20.0;

Demo 02 · Near-real-time streaming

02Kafka → TPT STREAM

A live Kafka topic, streamed into Teradata with the TPT Kafka Access Module — rows visible in Vantage every ~5 seconds for as long as the feed runs.

Latency tier: Near real-time (200ms–5s) Feature: tbuild -l 5 latency flush
What it demonstrates
  • The TPT Kafka Access Module (libkafkaaxsmod.so) connecting to a live topic and streaming pipe-delimited messages into Teradata with no intermediary file.
  • tbuild -l 5 — the latency-interval flag that forces STREAM to flush its internal buffers and commit rows every 5 seconds, even against a continuously-producing Kafka feed.
  • Format='DELIMITED' with an all-VARCHAR schema, then typed conversion (FLOAT, INTEGER, BYTEINT, DATE, TIMESTAMP(3)) inside the APPLY INSERT.
  • A partitioned target table (PPI on pos_date) — STREAM inserts directly into the correct partition.
  • Graceful shutdown: Ctrl+C kills the producer; TPT drains remaining buffered messages, then exits cleanly.
How to run
terminal
# Continuous streaming (default); press Ctrl+C to stop
bash demos/02-kafka-tpt-stream/run.sh

# Bounded mode — 100 messages; exits automatically
bash demos/02-kafka-tpt-stream/run.sh --bounded
Why -l matters. Without it, STREAM only flushes at end-of-source — which never fires while a live producer keeps the Kafka idle timeout from triggering. Rows would sit buffered and invisible until you stopped the feed. Source: TPT Reference Guide, B035-2436-103K.
How it works
1

Reset state

BTEQ truncates adsb_positions and drops STREAM operator work tables; the Kafka topic is deleted and recreated so partition offsets start clean.

2

TPT STREAM job starts (background), with -l 5

DataConnector PRODUCER + Kafka Access Module connect with AccessModuleInitStr: -M C -T <topic> -B <broker> -P 0 -W 30 (30s drain window).

3

Python producer runs continuously

10 synthetic aircraft, one position update each per second. Each message: icao24|callsign|lat|lon|...|ts\n — the trailing \n is the DELIMITED record terminator.

4

Every 5 seconds: flush

STREAM's internal buffers flush on the latency interval — roughly 50 rows committed to adsb_positions per cycle.

5

Ctrl+C → graceful drain

Producer killed → Kafka idle timeout (-W 30) fires → STREAM flushes whatever's buffered and exits.

Key technical constraints
ConstraintDetail
tbuild -l <seconds>Required for continuous streaming — without it, flush only happens at end-of-source, which never fires with a live producer.
Two different -W flagstbuild -W is the subprocess spawn timeout; the -W inside AccessModuleInitStr is the Kafka idle timeout — unrelated options that happen to share a letter.
AccessModuleName / AccessModuleInitStrNamed attributes like TopicName are silently ignored — configuration goes through CLI-style flags instead.
All schema columns VARCHARFormat='DELIMITED' requires VARCHAR/CLOB; typed conversion happens via CAST in APPLY INSERT.
\n record terminatorMessages without it get concatenated into one giant record, overflowing fields.
LogTable / ErrorTableMust be named explicitly — STREAM defaults to DBC-prefixed names that require DBC privileges.

Demo 03 · Object storage ingestion

03Kafka Connect → MinIO CSV → NOS

Weather observations stream through a Kafka Connect S3 Sink into time-partitioned MinIO folders, then get queried and incrementally loaded via Teradata Native Object Store with partition pruning.

Latency tier: Microbatch (~5 min) Feature: PATHPATTERN partition pruning
What it demonstrates
  • Kafka Connect S3 Sink (ByteArrayFormat, flush.size=1, TimeBasedPartitioner) landing one CSV file per Kafka message under a plain time-partitioned path: YYYY-MM-DD/HH/.
  • READ_NOS with RETURNTYPE('NOSREAD_KEYS') to enumerate exactly which partition folders and files Kafka Connect wrote.
  • CREATE FOREIGN TABLE with PATHPATTERN — NOS partition pruning, 10–100× faster on large datasets since object listing and fetching skip non-matching partitions entirely.
  • Incremental load pattern: the FOREIGN TABLE covers the full MinIO path (all history); each run's INSERT INTO weather_obs scopes to the current hour's folder only.
  • --fresh flag for a full clean-slate reset (purges MinIO and clears all weather_obs rows).
How to run
terminal
# Accumulates this hour's data into weather_obs
bash demos/03-kafka-csv-minio/run.sh

# Full reset: purge MinIO + clear all weather_obs rows
bash demos/03-kafka-csv-minio/run.sh --fresh

Runtime: ~11 minutes for the default 3 batches at 5-minute intervals.

How it works
1

Producer publishes complete CSV batches

One Kafka message = one complete CSV file, header included: 5 stations × 6 offsets = 30 rows, every 5 minutes.

2

Kafka Connect S3 Sink writes it straight through

ByteArrayFormat writes message bytes as-is; flush.size=1 means a new file lands after every single message; TimeBasedPartitioner resolves the path to s3://demo-csv/raw/weather-csv/2026-06-19/14/....

3

NOS FOREIGN TABLE prunes by path

PATHPATTERN ('$var1/$var2/$var3/$var4/$var5') names each path segment. WHERE $var3 = '2026-06-19' AND $var4 = '14' eliminates every other partition before any I/O happens.

4

Incremental INSERT into weather_obs

Header rows are rejected by type-cast failure (CAST('station_id' AS TIMESTAMP) fails cleanly). Prior hours already in weather_obs are left untouched — data accumulates across runs.

Key NOS design rules
RuleDetail
PATHPATTERNThe most important NOS performance lever — eliminates file listing for non-matching partitions entirely.
PARTITION BY COLUMNParquet/JSON-only on 20.x — adding it to a CSV foreign table triggers error 3706. Omit it; string WHERE clauses on path variables still prune correctly.
$var vs ${VAR}${CURRENT_YEAR} (curly braces) is replaced by a perl preprocessor at script-build time; $var3 is a Teradata NOS path variable resolved at query time.
HEADER('TRUE')Does not suppress header rows from COUNT(*) — they appear in a raw SELECT and are rejected only at the typed INSERT step, via cast failure.
STOREDASNot accepted for CSV in CREATE FOREIGN TABLE USING on 20.x — omit it; CSV is the default.
DEFINER TRUSTEDEXTERNAL SECURITY DEFINER TRUSTED resolves the auth object in the table's own database; INVOKER TRUSTED would look in the session user's database instead.
Tables & queries
CREATE MULTISET FOREIGN TABLE weather_nos_ft ,FALLBACK ,
  EXTERNAL SECURITY DEFINER TRUSTED minio_nos_auth
(
  Location          VARCHAR(2048) CHARACTER SET UNICODE CASESPECIFIC,
  station_id        VARCHAR(4),
  observation_ts    VARCHAR(30),
  temperature_c     VARCHAR(10),

  station_id       CHAR(4)       NOT NULL,
  observation_ts   TIMESTAMP(0)  NOT NULL,
  temperature_c    DECIMAL(5,1),
  wind_speed_kts   SMALLINT,
  wind_direction   SMALLINT,

-- Path-filtered NOS query: reads only the current-hour partition
SELECT station_id,
       CAST(TRIM(observation_ts) AS TIMESTAMP(0) FORMAT 'YYYY-MM-DDBHH:MI:SS') AS obs_ts,
       CAST(TRIM(temperature_c) AS DECIMAL(5,1)) AS temp_c,
       conditions
FROM demo_db.weather_nos_ft
WHERE $var3 = '2026-06-19'
  AND $var4 = '14'
ORDER BY obs_ts DESC;

-- Aggregates across all accumulated hours
SELECT station_id,
       COUNT(*)            AS obs_count,
       AVG(temperature_c)  AS avg_temp_c,
       MAX(wind_speed_kts) AS max_wind_kts
FROM demo_db.weather_obs
GROUP BY station_id
ORDER BY station_id;

NOS asks "can I read this file?" — it doesn't ask "can I trust this table?" NOS is a stateless, schema-at-query-time read of raw files: no ACID, no caching, no warm-up benefit between queries, max 4 concurrent reads. That's exactly right for a landing zone you don't own the lifecycle of — which is why this demo is a good fit, and why Demo 04 reaches for Open Table Format instead once the requirement shifts to a governed, multi-engine table. Demo 04 · Open lakehouse

04Kafka → Flink → Iceberg → Teradata OTF

Flink SQL streams ADS-B messages straight into an Apache Iceberg table — Parquet on MinIO, metadata in Hive Metastore. Teradata queries the live table through a DATALAKE object, no ETL, no COPY, no TPT. New rows appear within ~30 seconds of ingestion.

Latency tier: Near real-time (30s checkpoint) Feature: Open Table Format / DATALAKE
What it demonstrates
  • Flink SQL checkpointing as the Iceberg commit mechanism: each 30-second checkpoint atomically commits a new Iceberg snapshot — and Teradata sees it on the very next SELECT.
  • The DATALAKE object — Teradata's OTF interface to an Iceberg catalog; one DDL statement connects Hive Metastore + MinIO, after which tables are queried via <datalake>.<namespace>.<table> 3-part notation.
  • TD_SNAPSHOTS() table function lists committed Iceberg snapshots — the growing history as streaming continues.
  • The open-lakehouse pattern: Flink writes Parquet data files; Teradata, Spark, and Trino can all query the same files simultaneously through the Iceberg catalog.
  • Iceberg partitioning by pos_date (daily) — partition pruning carries through to Teradata OTF queries.
How to run
terminal
# Continuous streaming (default); press Ctrl+C to stop
bash demos/04-kafka-flink-iceberg/run.sh

# Bounded mode — 200 messages; exits automatically
bash demos/04-kafka-flink-iceberg/run.sh --bounded
How it works
1

Reset

Flink SQL client drops the Iceberg table (removing Parquet + metadata from MinIO); the DATALAKE is dropped from Teradata; the Kafka topic is deleted and recreated.

2

DATALAKE setup, once per session

CREATE DATALAKE demo_iceberg: CATALOG_TYPE='hive', HMS at HOST_IP:9083, STORAGE_ENDPOINT=http://HOST_IP:9000 (MinIO, path-style, no SSL).

3

Flink streaming INSERT

Creates a Hive catalog (Iceberg Flink connector → Hive Metastore); CASTs + TO_TIMESTAMP() shape rows into Iceberg Parquet files on MinIO. Checkpoint every 30s (EXACTLY_ONCE) → one atomic Iceberg snapshot per checkpoint. The SQL client exits after submitting; the job keeps running in the Flink cluster.

4

Monitoring loop

Every 30 seconds: SELECT COUNT(*) + MAX(ts) FROM demo_iceberg.demo.adsb_positions from Teradata, via OTF.

5

Graceful shutdown (Ctrl+C)

Producer killed → 35s wait (slightly longer than the checkpoint interval) → final checkpoint commits the last rows → Flink job cancelled via REST (PATCH /jobs/{id}?mode=cancel).

Key OTF design rules
RuleDetail
DATALAKE, not FOREIGN TABLEIceberg tables are queried via CREATE DATALAKE with CATALOG_TYPE('hive') — a different object family from NOS.
HOST_IP everywhereTeradata is external to Docker; CATALOG_LOCATION and STORAGE_ENDPOINT need the host's real IP from .env, not container hostnames.
S3_PATH_STYLE_ACCESS('true')Required for MinIO — it uses path-style S3 URLs, not virtual-hosted-style.
S3_SSL_ENABLED('false')Required — MinIO in this stack runs plain HTTP.
Namespace creationCreated by Flink (CREATE DATABASE IF NOT EXISTS), not Teradata — CREATE DATABASE via DATALAKE from Teradata raises error 7825.
Checkpoint-boundary visibilityQueries between checkpoints return the previous snapshot's data — rows are visible in batches of ~30s, not row-by-row.

Iceberg's manifest-list → manifest → data-file metadata tree gives Teradata ACID reads, time travel, and schema evolution against the same Parquet files Flink, Spark, or Trino are writing — without anyone copying data between engines. Demo 05 · Reverse enrichment

05Flink Lookup Join ← Teradata

The ADS-B stream carries only ICAO24 identifiers. Teradata holds the master aircraft_ref table — registration, type, operator, country. Flink enriches each message in-flight with a JDBC Lookup Join against Teradata, then writes the enriched rows to Iceberg. This reverses Demos 02–04: instead of pushing data into Teradata, Flink pulls reference data from it.

Latency tier: Near real-time (30s checkpoint) Feature: Teradata as enrichment source
What it demonstrates
  • Teradata as an enrichment source — the JDBC Lookup Join runs SELECT … WHERE icao24 = ? against Teradata via the terajdbc driver; results are cached per a configured TTL, keeping Teradata load minimal.
  • Cache TTL and live invalidation — with a 30-second TTL, an UPDATE to aircraft_ref propagates into newly enriched Iceberg rows within one checkpoint window.
  • LEFT JOIN graceful degradation — ICAO24 codes with no matching reference row get UNKNOWN defaults instead of being silently dropped.
  • Teradata as both source and destination — aircraft_ref is the lookup source; enriched_positions in Iceberg is the OTF query target back in Teradata.

Flink SQL key excerpts
-- Processing-time attribute — required for lookup join temporal syntax
CREATE TEMPORARY TABLE kafka_adsb (
    icao24    STRING,
    ...
    proc_time AS PROCTIME()
) WITH ('connector' = 'kafka', ...);

-- Teradata JDBC lookup table
CREATE TEMPORARY TABLE aircraft_ref (
    icao24        STRING,
    registration  STRING,
    aircraft_type STRING,
    operator      STRING,
    country       STRING,
    PRIMARY KEY (icao24) NOT ENFORCED
) WITH (
    'connector'                                = 'jdbc',
    'url'                                      = 'jdbc:teradata://<TD_HOST>/DATABASE=demo_db,...',
    'table-name'                               = 'aircraft_ref',
    'lookup.cache'                             = 'PARTIAL',
    'lookup.partial-cache.max-rows'            = '10000',
    'lookup.partial-cache.expire-after-write'  = '30s'
);

-- Temporal lookup join
INSERT INTO enriched_positions
SELECT a.icao24, ..., r.registration, r.aircraft_type, r.operator, r.country
FROM kafka_adsb a
LEFT JOIN aircraft_ref FOR SYSTEM_TIME AS OF a.proc_time AS r
    ON a.icao24 = r.icao24;
-- 1. Observe Ryanair rows in Teradata OTF showing operator='Ryanair'
SELECT icao24, operator FROM demo_iceberg.demo.enriched_positions
WHERE icao24 = '3f7062' ORDER BY ts DESC SAMPLE 3;

-- 2. Update the reference table in Teradata
UPDATE demo_db.aircraft_ref WHERE icao24 = '3f7062'
SET operator = 'Ryanair DAC';

-- 3. Wait ~35s (cache TTL expires; next Kafka messages re-query Teradata)

-- 4. New enriched rows show the updated operator
SELECT icao24, operator, ts FROM demo_iceberg.demo.enriched_positions
WHERE icao24 = '3f7062' ORDER BY ts DESC SAMPLE 5;
-- operator transitions from 'Ryanair' → 'Ryanair DAC' at the cache boundary
SELECT
    TRIM(icao24)        AS icao24,
    TRIM(callsign)      AS callsign,
    COUNT(*)            AS positions,
    MAX(registration)   AS registration,
    MAX(aircraft_type)  AS ac_type,
    MAX(operator)       AS operator,
    MAX(country)        AS country
FROM demo_iceberg.demo.enriched_positions
GROUP BY 1, 2
ORDER BY 1;
PARTIAL vs FULL cache

Always PARTIAL. FULL mode loads the entire dimension table into Flink heap before processing starts — fine for 10 rows in this demo, an OOM guarantee for a production dimension table with millions of rows. PARTIAL caches only the keys that have actually appeared in the stream.

Why LEFT, never INNER

With LEFT JOIN, an unmatched ICAO24 passes through with null enrichment — visible and filterable downstream. With INNER JOIN it's silently dropped. In a streaming pipeline, silent data loss is strictly worse than a null field.

Same destination, six different roads in.

Every demo lands data in Teradata Vantage. What differs is the latency tier, the operator doing the work, and how much of the journey happens before Teradata ever sees a row.

BFS vs NOS vs OTF — the three storage tiers behind Demos 02–05

Demo 02 writes straight into Teradata's own block storage (BFS). Demo 03 reads files NOS doesn't own or manage. Demos 04–05 read a governed Iceberg table through OTF. These aren't competing options — they're complementary tiers, and most real architectures use all three.

BFS

Data you serve at scale

LatencySub-second (<100ms)
CostHighest per TB
FormatNative Teradata

Full MPP parallelism, thousands of concurrent users. Mission-critical, high-concurrency workloads with a real SLA.

OTF

Data you share across engines

LatencySeconds (cache-accelerated)
CostMedium (object storage)
FormatIceberg v2 / Delta Lake v3

ACID + time travel on object storage, readable by Teradata, Spark, Trino, and Flink without replication. Teradata's strategic default for new data products.

NOS

Data you consume or archive

Latency5–30 seconds (variable)
CostLowest per TB
FormatRaw files (Parquet, CSV, JSON)

Stateless file scanning, no ACID, no caching between queries. Right for raw external drops and cold archival via WRITE_NOS.
